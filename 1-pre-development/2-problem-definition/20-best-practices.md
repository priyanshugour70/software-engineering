## 20 – Best Practices for Problem Definition

This file summarizes **practical habits and patterns** that lead to strong Problem Definition.

We group best practices into:

- A. Mindset
- B. Process
- C. Collaboration
- D. Documentation

---

### A. Mindset Best Practices

#### 1. Separate Problem from Solution

- Always be able to state the problem **without referring to a specific solution**.
- If your statement starts with:
  - “We need to build…”,  
  you are likely in solution space.

---

#### 2. Start from Reality, Not Opinions

- Anchor problem statements in:
  - real user stories,
  - real metrics,
  - real processes.
- Opinions and intuition can spark hypotheses, but **evidence** should shape final wording.

---

#### 3. Embrace Iteration

- Expect problem statements to **evolve** as you:
  - learn more,
  - talk to more stakeholders,
  - see more data.
- Treat early drafts as **working hypotheses**, not final truths.

---

### B. Process Best Practices

#### 4. Timebox Problem Definition

- Don’t let it run indefinitely.
- Define a:
  - start and end date,
  - review checkpoints.

This:

- forces decisions,
- avoids endless analysis.

---

#### 5. Link Problems to Opportunities and Strategy

- Always show:
  - which **opportunity** (from phase 1) a problem comes from,
  - which **strategic goal** it supports.

This:

- keeps work aligned,
- makes it easier to justify prioritization.

---

#### 6. Use Frameworks, but Keep Them Light

- Use tools from `04-frameworks.md`:
  - 5 Whys,
  - current vs desired state,
  - problem templates.
- Avoid turning them into:
  - heavy processes,
  - complex diagrams nobody uses.

Goal:

- **clarity**, not complexity.

---

### C. Collaboration Best Practices

#### 7. Involve Key Functions Early

- Don’t define problems alone as product.
- Include:
  - business owner,
  - ops,
  - risk/compliance (where needed),
  - engineering,
  - data.

This:

- surfaces constraints,
- builds ownership of the problem across teams.

---

#### 8. Make Workshops Concrete

- Bring:
  - data snippets,
  - real customer quotes,
  - process snapshots.
- Ask:
  - “Does this match what you see?”
  - “What’s missing?”

Avoid:

- purely abstract discussions with no grounding.

---

#### 9. Explicitly Resolve or Document Disagreements

- When stakeholders disagree:
  - don’t smooth it over with vague wording.
- Either:
  - work to resolve the disagreement, **or**
  - document the disagreement as part of the problem definition.

This builds trust and transparency.

---

### D. Documentation Best Practices

#### 10. Keep Problem Docs Short and Readable

- Aim for **1–3 pages** per problem, not 30.
- Use:
  - headings,
  - bullets,
  - simple language,
  - visuals when helpful.

---

#### 11. Always Include Metrics and Evidence

- For each problem, include:
  - baseline metrics,
  - qualitative insights,
  - links to data sources.

This:

- makes conversations more objective,
- helps later measurement.

---

#### 12. Track Version and Ownership

- Clearly state:
  - document version,
  - date,
  - owner.
- Note:
  - major changes over time,
  - who signed off.

Helps:

- downstream teams know which version to trust.
