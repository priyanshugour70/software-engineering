## 02 – Objectives of Problem Definition

This file explains **what success looks like** for the Problem Definition phase.  
Use it as a **north star** for your work and as a review checklist.

---

### 1. Primary Objective (One Sentence)

The main objective is to produce **clear, agreed, and testable problem statements** that:

- are grounded in **evidence**,
- have **well‑defined scope and boundaries**,
- and specify **measurable outcomes**, so downstream teams can confidently invest in solving them.

---

### 2. Key Outcomes You Should Achieve

#### 2.1 A Clear, Written Problem Statement

For each priority opportunity, you should end up with a **concise, structured problem statement** that answers:

- **Who** is affected?
- **What** is happening today (symptoms)?
- **Why** does this matter (impact on users and business)?
- **Where/When** does it happen (context, journey, segment)?
- **How** will we know it is solved (outcomes and metrics)?

If multiple readers can interpret the statement in **different ways**, it is not yet clear.

---

#### 2.2 Well-Defined Scope and Boundaries

The scope should explicitly state:

- What is **in scope**:
  - segments, journeys, geographies, channels, processes.
- What is **out of scope** (for now):
  - what will not be addressed by this initiative.

Outcome:

- Teams know **where to focus** and what is **not part** of this problem.
- Prevents “boiling the ocean” and endless scope creep.

---

#### 2.3 Agreed Success Metrics and Outcomes

For each problem, you should define:

- **User outcomes**:
  - what improves for users (e.g., time saved, fewer errors, higher satisfaction).
- **Business outcomes**:
  - what changes for the organization (e.g., higher completion, lower cost to serve, lower risk).

With **preliminary target values**, such as:

- “Reduce onboarding time from 3 days to 30 minutes.”
- “Increase completion rate from 60% to 80%.”

These don’t have to be perfect, but they must be:

- **specific**, and
- **measurable**.

---

#### 2.4 Explicit Constraints and Assumptions

You should produce a **constraints & assumptions register** that lists:

- **Constraints**
  - Regulatory and legal constraints.
  - Technical/platform constraints.
  - Operational constraints (capacity, processes, SLAs).
- **Assumptions**
  - About user behavior or adoption.
  - About internal readiness for change.

Objective:

- Avoid surprises later (“we can’t legally do this”, “this system can’t support that flow”).
- Make it clear **what needs validation** in subsequent phases.

---

#### 2.5 Stakeholder Alignment

Different functions (product, business, engineering, risk, operations, support) should:

- **recognize the same problem** when they describe it,
- agree broadly on:
  - severity,
  - scope,
  - and desired outcomes.

Signs you’ve met this objective:

- In workshops or reviews, stakeholders **repeat the same core problem** in their own words.
- Discussions are about **how to address** the problem, not **what the problem is**.

---

### 3. Secondary (But Important) Objectives

#### 3.1 Create Reusable Problem Artifacts

Problem statements can:

- be reused as **reference** for:
  - later research,
  - design,
  - rollout and training,
- help onboard new team members quickly.

Objective:

- Ensure problem documents are:
  - easy to find,
  - easy to read,
  - versioned for updates.

---

#### 3.2 Improve Organizational Understanding of Current State

During Problem Definition, you often:

- map current processes,
- collect data,
- surface pain points.

Objective:

- Leave the organization with a **better shared understanding** of:
  - how things work today,
  - where friction and waste occur.

This remains valuable even as solutions evolve.

---

#### 3.3 Set Up Effective Downstream Work

Good Problem Definition should:

- make it **easier** for:
  - researchers to plan studies,
  - designers to explore solutions,
  - engineers to estimate,
  - business and risk to evaluate impact.

If downstream teams still need to **re‑do problem discovery** from scratch, the Problem Definition phase has not achieved its goal.

---

### 4. What “Good” vs “Bad” Problem Definition Looks Like

#### 4.1 “Good” Problem Definition

- Problem statements are:
  - **specific**, **plain‑language**, and **solution‑agnostic**.
- Impact is:
  - **quantified** where possible (baseline metrics + target ranges).
- Scope is:
  - tight enough to tackle in a **realistic initiative**,
  - but broad enough to matter.
- Stakeholders:
  - can explain the problem similarly,
  - in a few sentences.

#### 4.2 “Bad” Problem Definition

- Statements like:
  - “We need a new mobile app.”
  - “Improve customer experience.”
- No clear:
  - who, what, why now.
- No agreed metrics:
  - success becomes a matter of opinion.
- Wide or vague scope:
  - “Fix SME onboarding in all countries and all channels at once.”

---

### 5. Example: Objectives for a Problem Definition Sprint

Imagine a 3‑week Problem Definition sprint for **digital SME onboarding**.

The team sets explicit objectives:

1. **Produce 1–2 high‑quality problem statements**
   - for the highest‑priority opportunity from the previous phase.
2. **Define baseline metrics and targets**
   - e.g., current vs target:
     - onboarding time,
     - completion rate,
     - error rates,
     - call volume.
3. **Document scope and constraints**
   - In scope:
     - SMEs in Country X applying online and in branches.
   - Out of scope:
     - corporate onboarding, other countries.
4. **Align stakeholders**
   - Run at least:
     - 1 cross‑functional workshop to review and refine problem statements.

This makes it obvious, at the end, whether the sprint succeeded.

---

### 6. Checklist: Have We Met the Objectives?

Use this quick checklist before closing Problem Definition for a given opportunity:

- **Clarity**
  - [ ] Can the problem be explained clearly in 2–3 sentences?
  - [ ] Is it **solution‑agnostic**?
  - [ ] Is the target segment well defined?
- **Scope**
  - [ ] Is it clear what is **in scope** and **out of scope**?
  - [ ] Are affected processes, systems, and channels listed?
- **Evidence**
  - [ ] Are there links to:
    - [ ] data/metrics,
    - [ ] qualitative findings (interviews, workshops),
    - [ ] relevant documents (process maps, policies)?
- **Outcomes**
  - [ ] Do we have baseline metrics and **target ranges**?
  - [ ] Are both **user** and **business** outcomes considered?
- **Constraints & Assumptions**
  - [ ] Are key constraints listed (regulatory, technical, operational)?
  - [ ] Are important assumptions written down?
- **Alignment**
  - [ ] Have key stakeholders reviewed and agreed on the problem statement?

If many boxes are unchecked, iterate on the problem definition before moving on.
