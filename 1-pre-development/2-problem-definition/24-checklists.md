## 24 – Checklists for Problem Definition

This file provides quick **checklists** to use during Problem Definition.

We include:

- A. Starting a Problem Definition sprint
- B. Reviewing a single problem statement
- C. Before handing over to downstream teams

---

### A. Starting a Problem Definition Sprint – Checklist

**Scope & Objectives**

- [ ] Have we written a **scope & plan** (see `23-templates.md`)?
- [ ] Are we clear on:
  - [ ] which **opportunity** this relates to?
  - [ ] which **segments** and **journeys** are in scope?
  - [ ] what **decisions** this Problem Definition should enable?

**Team & Stakeholders**

- [ ] Do we have a named **PM/owner**?
- [ ] Do we have engaged representatives from:
  - [ ] Business / sponsor
  - [ ] UX/Research
  - [ ] Engineering
  - [ ] Data/BI
  - [ ] Ops/Process
  - [ ] Risk/Compliance (if relevant)

**Timebox**

- [ ] Start and end dates agreed.
- [ ] Key milestones defined:
  - [ ] data review,
  - [ ] draft statements,
  - [ ] validation workshop,
  - [ ] finalization/hand‑over.

---

### B. Reviewing a Single Problem Statement – Checklist

Use this when you want to check if a problem statement is “good enough”.

**Clarity**

- [ ] Can we explain the problem in **2–3 sentences**?
- [ ] Is the **who / what / where / why it matters** clear?
- [ ] Is it free of heavy jargon?

**Solution-Agnostic**

- [ ] Does the statement avoid specifying a particular solution?

**Scope**

- [ ] Is **scope** explicitly stated (in/out)?
- [ ] Is it narrow enough to tackle but big enough to matter?

**Evidence**

- [ ] Does it include or reference:
  - [ ] relevant **metrics** (baseline),
  - [ ] key **qualitative insights** (e.g., user or ops feedback)?

**Outcomes**

- [ ] Are **desired outcomes** (user and business) described?
- [ ] Are there **target ranges** for key metrics?

**Constraints & Assumptions**

- [ ] Are major **constraints** (reg, tech, ops) documented?
- [ ] Are key **assumptions** written down with owners?

**Alignment**

- [ ] Have key stakeholders reviewed and broadly agreed with the statement?

If several boxes are unchecked, refine before using the statement to drive design and delivery.

---

### C. Before Handover – Checklist

Use this when you think Problem Definition is done for a given problem and you’re ready to hand it off.

**Artifacts Complete**

- [ ] Problem Statement Document created and up to date.
- [ ] Constraints & Assumptions Register filled.
- [ ] Current State & Metrics summary included or linked.

**Traceability**

- [ ] Problem is linked to:
  - [ ] its originating opportunity,
  - [ ] relevant strategies/OKRs.
- [ ] Planned epics/initiatives link back to this problem.

**Stakeholders**

- [ ] Sponsor has reviewed and accepts:
  - [ ] scope,
  - [ ] ambition level.
- [ ] Engineering lead, ops, and risk/compliance (if needed) have contributed.

**Next Steps**

- [ ] Clear owner(s) identified for:
  - [ ] further user research,
  - [ ] business case work,
  - [ ] solution design.
- [ ] Immediate next actions are agreed (what happens in the next 2–4 weeks).

If these are satisfied, the problem is **ready to move** into the next phases.
